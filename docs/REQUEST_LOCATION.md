# 时间不准确时定位客户请求

在 `/cases/new` 的“线索来源”中，展开“时间不准或没有 Request ID？按特征查找”。

1. 在下方客户问题中填写客户原话，保留错误的原始时间描述。
2. 输入并核对 new-api 客户用户名，勾选账号确认。所有查询始终固定在这个账号内。
3. 可填写客户记忆中的时间、时区、模型、渠道、stream 设置、错误关键词或 Request ID。回忆线索参与排序，不作为必须匹配的筛选条件。
4. 若 Request ID 从原始日志复制，可勾选精确匹配；这时查询忽略客户时间，不会因错误日期错过该 ID。
5. 点击“按特征定位请求”，查看匹配依据、冲突、实际时间、部分结果提示和针对性追问。需要时调整线索重新查询。
6. 选择“确认此请求并导入”，再保存案件或开始诊断。确认请求对应关系与确认故障根因是两个独立步骤。

更换账号或修改线索会取消旧查询、清空旧候选，防止导入过期结果。已经确认导入的日志可在原工作台核对。

## 检索策略

定位采用独立 LangGraph 状态图：`plan → search → rank → 条件继续 search 或结束`。`search_request_logs` 是新增的 LangChain 标准工具，服务器在创建工具时绑定客户账号与已确认的筛选条件，工具调用参数只允许时间、页码和页大小。

有百炼密钥时，模型从脱敏的客户原话中提取模型、请求标识与关键词。提取值必须出现在原话中，并且只能作为软线索；模型不能替换客户账号、提升线索确认级别或决定扩大查询范围。未配置模型或提取失败时，仍可使用已填字段和本地关键词提取。

时间支持带年份的日期与时间、带时区的 ISO 时间，以及“今天、昨天、前天”和常见上午、下午、晚上表达。相对日期按所选 UTC 偏移计算，不依赖服务器所在时区。时区使用固定 UTC 偏移；夏令时地区需选择当时正确的偏移。无法可靠解析的日期不会猜成确定事实，存在其他有效线索时仅尝试最近一天、三天、七天。

有可解析时间时，依次尝试原始时间、可能将 UTC 当作本地时间、上午下午偏差、前后一天和日期前后七天。所有窗口排除未来时间，重叠日志去重。只有日期或大致时段时，显示的解释时间是生成窗口的参考点，不是已确认的发生时间。

最多发起六次日志接口请求、扫描五百条记录，每页固定一百条；分页也消耗请求预算。若较早窗口的日志很多，可能在尝试后续时间假设前就触及预算，页面会明确显示尚未查完的范围。需要时可补充已确认的请求标识，或提供更多特征再查。

## 排序、归组与追问

排序优先使用请求标识，其次模型、渠道、错误原文、stream 和时间接近程度。分数是相对排序值，不是置信概率，不会触发自动确认。接口没有直接按错误关键词或 HTTP 状态码筛选的能力，关键词只在返回的日志正文中匹配，系统不会从消耗日志推断成功或 HTTP 200。

时间接近并且模型与渠道相同、共享上游请求标识，或令牌名称与错误原文相同的请求，可显示为可能相关的一轮尝试，并按实际时间排列。分组属于待核对线索，不会据此写入确定的重试次数或成功结论。多条候选无法区分时，优先根据模型、渠道或 stream 的差异追问；仍无法区分时要求原始请求标识或错误原文。

## 结果与保存

接口使用 `POST /api/integrations/new-api/search`，结果区分：候选、已查范围无匹配、检索不完整、查询失败、线索不足。权限不足、限流、网络失败、响应格式错误、后台拒绝查询都不会被解释为客户时间错误，发生失败后停止扩展范围。日志已过期或原始字段未记录时，只能说明现有日志无法定位，不能证明请求没有发生。

确认导入后，保留实际发生时间及已脱敏日志，并在案件日志中记录 `request_location_review`：原始时间、解释时间、时区、账号、线索来源与级别、各轮覆盖范围、停止原因、匹配与冲突、人工确认时间，以及独立的 `rootCauseConfirmed: false`。工作台保存时继续使用既有服务端校验和脱敏。为满足上下文长度限制，必要时缩短日志预览，完整定位依据不会静默截断；极长依据会提示缩小查询后再导入。

该功能沿用 `NEW_API_BASE_URL`、`NEW_API_ACCESS_TOKEN`，需要管理员日志查询权限，不需要数据库迁移。它运行于现有内部运维工作台的权限环境；账号确认是查询范围约束，不是新增的登录或租户授权机制。

## 验证

单元测试覆盖时区、上午下午偏差、无效日期、固定账号、上游与网关 ID 区分、模型提取回退、分页预算、后台拒绝、失败与取消。浏览器测试覆盖候选确认、原话与定位依据保存，以及修改账号后候选失效。模型和 new-api 查询使用合成响应进行测试；未通过测试查询真实客户日志。
